# 4개 독립 FAQ 평가셋 v4

기존 Excel·KT·SKT·LG U+가 **각각** 같은 README 검증 목적을 만족하도록 보강한 작성본이다. 전체 합계로 한 데이터셋의 부족한 목적을 대신 채우지 않는다. 데이터셋 작성과 모델 실행은 분리하며, 후속 Ollama·vLLM 측정은 [serving_test](serving_test/README.md)에 저장한다.

**현재 상태:** 15개 공통 목적의 작성 범위와 구조 검사는 완료했다. 독립 의미 검수, 복수 정답의 완전성, 부재 사실의 확정은 대기 중이다. 최종 벤치마크·임계값 피팅 가능 상태는 false다. 목적별 10개 근거 시나리오는 작성 최소치이며 95%/99% 품질을 증명하는 표본 수가 아니다.

질문·FAQ 근거 검수 화면 (로컬 전용: `review/index.html`) · 목적별 범위 JSON (로컬 전용: `data/coverage_matrix.json`) · 자동 검증 (로컬 전용: `data/validation_report.json`) · [평가 계약](evaluation_contract.json)

**2026-10-07 후속 측정 완료:** 동결된 1,918질문을 Ollama·vLLM에 각각 전부 입력했다. 13개 구조 × 8회 결과와 후보 로그 1,216,070행 검증, 부하·반복·검색 Context 공격 진단을 실행 보고서 (로컬 전용: `serving_test/outputs/run-v4/comparison.md`)에 정리했다. 데이터셋·정답 파일은 그대로이며, 독립 의미 검수 대기 상태와 최종 벤치마크/임계값 피팅 제한도 유지한다.

## 각 데이터셋이 만족하는 15개 공통 목적

아래 숫자는 **서로 다른 근거 시나리오 수**다. 같은 사실 집합의 번역·오타·반복 표현은 하나로 센다. 복수 사실의 조합은 별도 시나리오지만 근거가 겹칠 수 있으므로 통계적으로 독립이라고 주장하지 않는다. NO_FAQ는 미지원 사실 단위, 모호한 질문은 누락된 문맥 종류로 센다. 행 수와 근거 단위 수는 JSON에 함께 기록했다.

## Retrieval 구조 비교에 필요한 진단 묶음

| 데이터셋 | 질문에 직접 검색 단서 | 답변에만 세부 단서 | 여러 문서가 필요한 질문 | 오답 후보가 명시된 질문 |
|---|---:|---:|---:|---:|
| 기존 Excel | 10 | 10 | 25 | 12 |
| KT | 10 | 10 | 10 | 12 |
| SKT | 10 | 10 | 10 | 10 |
| LG U+ | 10 | 10 | 10 | 20 |

근거 위치 묶음은 수동 지정한 80개 사례 (로컬 전용: `authoring/cue_panels.jsonl`)다. “답변에만 단서”는 지정한 원천 FAQ 문서의 세부 상품·조건·절차를 가리킨다. 다른 정답 FAQ의 질문에 그 단서가 있을 수 있으며 이를 필드로 드러낸다. 질문만으로 검색이 반드시 실패한다는 뜻이 아니다. 오답 후보는 작성자가 선정했으며 모델에서 높은 점수가 측정된 오답이라는 뜻이 아니다.

## 검색 정답과 응답 행동

- `faq_pairs.jsonl`: FAQ ID, 질문, 답변, 출처. 임베딩 대상이다.
- `user_questions.jsonl`: 새 사용자 질문, 허용 정답 ID 전체, 사실별 OR/AND 관계, 목적, 분할, 기대 행동. 평가 전용이다.
- `required_facts`: 코퍼스에서 답할 수 있는 사실만 포함한다. 각 사실 안의 `acceptable_faq_ids`는 OR, 여러 사실은 AND다.
- `unsupported_facts`: PARTIAL의 미지원 부분. FactRecall 분모에 넣지 않는다.
- `tool_requirements`: 개인·실시간 조회 13문항을 분리했다. 순수 조회 6문항은 NOT_APPLICABLE, FAQ+조회 7문항은 FAQ 하위 요구만 채점한다.
- `inputs/*.jsonl`: 모델에 전달할 question_id/query만 저장한다. 근거 ID·정답·목적 라벨은 들어가지 않는다.

NO_FAQ·CLARIFY·개인 조회의 Hit/MRR은 N/A다. PARTIAL이 지원 사실을 전부 검색하면 FactRecall=1일 수 있지만 전체 요청 해결로 계산하지 않는다. 생성 성공 여부는 별도로 측정한다. 이진 Calibration은 검수된 FAQ_EXISTS/NO_FAQ만 사용하며 PARTIAL·CLARIFY·TOOL_LOOKUP을 섞지 않는다.

문맥 질문은 `context_concat_v1` 규칙으로 대화 이력과 현재 질문만 연결한다. 정답용 독립 질문을 복사해 넣던 경로를 없앴다. LLM 재작성 성능은 측정하지 않으며, 모든 검색 구조에 같은 고정 입력을 사용하고 일반 검색과 별도 보고한다.

## README의 별도 실행·자료 의존 항목

| 항목 | 네 데이터셋에 적용한 규칙 | 상태 |
|---|---|---|
| 반복 | 데이터셋마다 10질문 × 10회 실행 계획. 문항 수는 10개 그대로 | manifest 준비, 미실행 |
| 문서 공격 | 데이터셋마다 10개 원문 보존 패치. 복제 코퍼스에만 명령문 추가 | fixture 준비, 미실행 |
| REAL_FAILURE | 실제 입력·당시 코퍼스·실제 Top-K·원인 모두 있어야 등록 | 인증된 서비스 실패 자료 미반영 |
| TEMPORAL_VERSION | 날짜 문자열과 정책 유효기간을 구분하고 실제 근거가 있을 때만 작성 | 날짜 후보 감사 목록, 버전 검수 대기 |

자료가 없다고 실제 실패나 과거 정책을 합성해서 채우지 않았다. 따라서 **15개 공통 목적 작성 완료**와 **README의 모든 실험 실행 완료**는 다르다. 항목별 상태 (로컬 전용: `data/readme_requirement_status.json`)는 네 데이터셋을 따로 기록한다. 문서 공격의 검색 순위·Context 전달·생성 지시 준수는 각각 채점하며 원본 인덱스와 캐시를 공유하지 않는다.

## 분할과 공정성

전체 분야 이름으로 통째로 분할하던 v3 방식을 바꿨다. 같은 사실·허용 FAQ·대조쌍·변형 원본·미지원 사실·복수 질문 구성 요소는 같은 연결 그룹에 묶고 약 50/25/25로 나눴다. 모든 분할은 해당 통신사의 전체 FAQ 코퍼스를 검색한다. 분할별 목적 수는 진단 범위 (로컬 전용: `data/diagnostic_coverage.json`)에 남긴다. 목적별 최소 10개는 데이터셋 전체 기준이며 각 split에 10개씩 있다는 뜻이 아니다.

코퍼스의 주제 비율은 서로 다르며 LG U+는 여행 상품 비중이 높다. 네 데이터셋을 섞은 평균으로 공정성을 주장하지 않는다. 데이터셋·목적별 결과를 먼저 보고 비교 가능한 검색 트랙 안에서 목적별 macro 평균을 사용한다. 원천 FAQ 전체를 동일 횟수로 질문화한 표본도 아니다. 모델 결과를 보고 좋은 문항만 고르지 않았으며, 알려진 연결 관계 밖의 의미 중복과 정답 누락은 독립 검수가 필요하다.

NO_FAQ와 PARTIAL은 정적 정보 부재 후보이며 전수 어휘 검색 목록이 독립 의미 검수를 대신하지 않는다. 특히 기술 세부정보를 묻는 부재 질문 비중과 소수 NO_FAQ 표본이 거절 성능을 왜곡할 수 있으므로 최종 피팅을 아직 허용하지 않는다. 추가한 문항은 결제 재시도·환불·분실 배상·구독 기록 등 가까운 주제의 누락 사실을 보강했다.

Dual Vector의 A Top-K + B Top-K 합집합은 최대 2K까지 늘어날 수 있다. 원시 합집합 Recall과 동일 최종 후보 수 비교를 별도로 기록한다. A~F 구조·점수·Margin·리랭커 입력을 고정한 뒤 Calibration에서 macro-F1을 최적화하고, 동률이면 FAQ 오거절이 적은 값을 선택한다. Holdout은 그 이후 고정 평가한다.

## 재생성 및 검사

아래 명령은 이 폴더 안의 v4만 생성하며 모델·서버를 실행하지 않는다.

```powershell
python authoring/create_additions.py
python authoring/create_cue_panels.py
python build_dataset.py
python build_fixtures.py
python build_review.py
python build_docs.py
python test_dataset.py
```

구조 검사에는 원본 해시 보존, 통신사 혼합 차단, 다른 통신사 정답/캐시 거부, 사실별 OR/AND, 부분 답변 분모, 조회 분리, 정답 없는 문항 N/A, 목적별 최소 범위, 근거 위치, 라벨 없는 문맥 입력, 결정적 빌드가 포함된다. 인코더 호출 검사는 fake encoder를 사용한다. 실제 검색 품질이나 의미 정답의 완전성을 인증하는 검사는 아니다.
