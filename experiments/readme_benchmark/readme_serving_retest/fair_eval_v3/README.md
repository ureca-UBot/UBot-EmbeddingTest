# FAQ 평가셋 v3 — 기존 / KT / SKT / LG U+

**임베딩 전에 하나의 데이터셋을 선택한다.** 각 데이터셋의 FAQ Q/A만 해당 인덱스에 넣으며, 사용자 질문도 그 데이터셋 안에서 검색한다. 데이터셋 ID는 정답 라벨이나 질문 내용으로 추론하지 않고 실행 설정으로 지정한다.

| 데이터셋 ID | FAQ 질문·답변 쌍 | 사용자 질문 | 출처 |
|---|---:|---:|---|
| `existing` | 1,024 | 331 | 기존 Excel FAQ 코퍼스 + 공정성 보완 v2 질문의 보존 사본 |
| `kt` | 1,099 | 745 | 새 JSONL의 KT |
| `skt` | 1,305 | 598 | 새 JSONL의 SKT |
| `lgu` | 131 | 168 | 새 JSONL의 LG U+ |
| 합계 | **3,559** | **1,842** | 서로 독립된 4개 검색 범위 |

새 통신사 질문은 **1,511개**다. 898개 원천 FAQ에서 요청 정보를 달리하여 작성한 기본 질문 1,156개, 동일 의미 대조 질문 250개, 복수 정보 질문 45개, 답변 가능성 질문 60개다. 대조 질문과 같은 FAQ에서 나온 질문을 통계적으로 독립된 표본으로 계산하면 안 된다.

질문·근거 검수 화면 (로컬 전용: `review/index.html`) · [고정 입력 명세](manifest.json) · 16개 자동 검사 결과 (로컬 전용: `data/validation_report.json`) · 분야·목적·상태별 통계 (로컬 전용: `data/quality_report.json`)

현재는 **작성자가 원문 근거를 확인한 합성 검수본**이다. 독립 의미 검수, 대체 정답의 완전성 확인, 정답 부재의 의미 검수는 남아 있다. 새 데이터셋으로 모델 서빙이나 calibration 피팅을 실행한 결과는 없다.

## 파일과 입력 계약

각 `datasets/<dataset_id>/`에 다음 파일을 따로 저장했다.

- `faq_pairs.jsonl`: `faq_id`, `question`, `answer`, 출처. 임베딩 대상 코퍼스다.
- `user_questions.jsonl`: 새 사용자 질문, `answer_faq_ids`, 사실별 정답, 분할·검수 라벨.
- `facts.jsonl`: 요청 정보 단위별 허용 FAQ와 원문 근거.
- `splits/development.jsonl`, `calibration.jsonl`, `holdout.jsonl`: 평가기용 라벨.
- `inputs/<split>.jsonl`: 모델용 `question_id`, `query` 두 필드만 포함한다.

사용자 질문 파일의 `answer_faq_ids`는 확인된 정답 FAQ ID의 **배열**이다. `expected_faq_ids`에도 같은 배열을 보존한다. 예를 들어 LG U+ 여행 SIM의 앱 SMS 인증과 은행·관공서 본인인증 차이를 묻는 `Q3-S0474-01`에는 한국어·영어 FAQ 두 문서를 허용한다.

```json
{
  "question_id": "Q3-S0474-01",
  "dataset_id": "lgu",
  "user_question": "LG U+ 여행용 음성·문자 SIM에서 택시 앱 SMS 인증과 관공서 본인인증은 둘 다 가능한가요?",
  "answer_faq_ids": ["FAQ-LGU-00e878336428", "FAQ-LGU-733424aef43b"]
}
```

하나의 요청 정보를 여러 FAQ가 똑같이 뒷받침하면 해당 사실의 `acceptable_faq_ids`에 모두 넣는다(OR). 여러 정보가 필요한 질문은 `required_facts`를 나누며, 모든 사실에 대한 근거를 각각 검색해야 완전 정답이다(AND). 합쳐 놓은 정답 ID 중 하나만 맞았다고 복수 정보 질문 전체를 성공으로 처리하지 않는다.

새 질문 중 정답 ID가 2개 이상인 질문은 KT 55개, SKT 47개, LG U+ 142개다. 이 수에는 동일 답변의 대체 FAQ와 복수 정보 질문이 모두 포함된다. 132개 기본 질문에 대체 문서 근거를 작성했고 그 정답을 동일 의미 대조 질문에 전파했다. 문자 유사도 후보는 별도 검수 큐에 두며 자동으로 정답에 추가하지 않았다. **현재 배열이 의미적으로 가능한 모든 정답을 누락 없이 포괄한다는 독립 검증은 완료되지 않았다.**

문맥 질문은 `dialogue_history`, 실제 후속 발화 `user_question`, 고정 재작성 `model_query`를 구분한다. 모든 엔진에는 같은 `model_query`를 넣는다. 재작성 모델의 품질이나 현재 발화만의 검색 성능을 측정한 것으로 해석하면 안 된다.

## 통신사 격리

`dataset.py`의 `Dataset('kt')`를 선택하면 KT 1,099개만 읽는다. SKT·LG U+·기존 코퍼스와 합친 파일은 실행 입력으로 제공하지 않는다. 작성용 전체 목록인 `authoring/corpus_catalog.jsonl`과 원문 보관용 `source/`는 모델 입력이 아니다.

- A: 선택한 코퍼스의 FAQ 질문만 임베딩한다.
- B: 같은 코퍼스의 질문 + 빈 줄 + 답변을 임베딩한다.
- A+B 합집합, sparse, multi-vector, reranker 역시 선택한 FAQ ID 범위 안에서 처리한다.
- 캐시는 데이터셋 ID·코퍼스 전체 해시·엔진·모델·표현 방식·문서 입력 형식·인코더 설정으로 분리한다. 설정에는 모델 revision, 정밀도, 최대 길이, 정규화, pooling 등을 명시해야 한다.
- 결과 경로에는 질문셋 해시와 분할도 포함한다. 데이터셋·엔진·구조가 다르면 임계값도 별도로 피팅한다.
- 로드 후 다른 코퍼스를 실수로 합쳐도 인코더를 호출하기 전에 오류를 낸다. 다른 통신사 정답·검색 결과 ID, 다른 설정의 캐시도 거부한다.

`Dataset.embed_corpus()`는 선택한 문서 텍스트만 인코더 콜백에 전달하는 접점이다. 이번 검증에서는 가짜 인코더로 전달 목록·범위·호출 차단을 확인했다. **Ollama/vLLM/TEI 실행기에 연결하여 실제 벡터를 만든 상태는 아니다.** 이전 `run_all.ps1`은 보존된 v1 실험이므로 그대로 실행하면 v3 측정이 되지 않는다.

이후 후보 로그에는 기존 요청 필드 16개를 유지하고 `dataset_id`, `question_id`, `expected_faq_ids`, `required_facts`, 코퍼스·질문셋 해시를 함께 기록한다. 기존 필드: `query`, `expected_faq_id`, `faq_id`, `retrieval_rank`, `retrieval_cosine`, `rerank_rank`, `rerank_score`, `window_count`, `winning_window_index`, `winning_window_text`, `winning_window_score`, `rank_delta`, `retrieval_a_rank`, `retrieval_a_cosine`, `retrieval_b_rank`, `retrieval_b_cosine`. 복수 정답을 첫 번째 ID로 축소하지 않는다. `rank_delta = retrieval_rank - rerank_rank`를 유지한다.

## 분할과 공정성 범위

| 데이터셋 | development | calibration | holdout | 연결 그룹 |
|---|---:|---:|---:|---:|
| existing | 155 | 85 | 91 | 90 |
| kt | 373 | 186 | 186 | 94 |
| skt | 299 | 150 | 149 | 70 |
| lgu | 114 | 40 | 14 | 11 |

신규 데이터는 원문 카테고리·동일 사실·대체 정답 문서·대조 질문·복수 정보·모호한 질문의 해석 후보를 연결하여 그룹 전체를 같은 분할에 둔다. 목표 비율은 50/25/25지만 연결된 내용을 억지로 쪼개지 않는다. 기존 데이터셋은 v2의 분할을 보존한다. 모든 분할의 인덱스에는 해당 데이터셋의 FAQ 전체를 넣는다.

**LG U+ holdout은 14개 중 FAQ 있음 7개와 부재 후보 7개뿐이다.** 원문의 카테고리가 넓고 한영 중복·복수 정보 질문이 연결되면서 큰 그룹 두 개가 생겼다. 이 holdout으로 안정적인 일반화 성능이나 최적 임계값을 주장할 수 없다. 독립 정책 단위 검수 후 더 세밀하게 그룹화하거나 새로운 정책군 자료를 확보해야 한다.

세 통신사에는 모두 15개 주 목적이 있지만 분할별·분야별로 같은 수를 강제하지 않았다. 출처의 194개 유효 브랜드/카테고리/언어 층에서 900개 FAQ를 선정했고, 본문 근거가 부족한 2개는 질문 작성에서 보류했다. FAQ마다 10개를 반복해서 채우지 않았다. 영어·한국어·혼합 질문 80묶음은 같은 정답과 분할을 공유한다. 오타·긴 배경·문맥 대조는 각각 30개다.

새 통신사별 답변 가능성 질문은 NO_FAQ 10개, PARTIAL 5개, 정보 부족 5개다. NO_FAQ에는 기술 상세 부재 후보, 개인·실시간 조회 요청, 범위 밖 질문이 섞여 있다. 이는 실제 운영 분포 표본이 아니다. 개인 조회 요청은 정적 FAQ만으로 실제 값에 답할 수 없다는 뜻이며, 서비스가 해당 조회 기능을 제공하지 않는다는 뜻이 아니다. 전체 코퍼스 키워드 감사 결과는 `data/absence_audit.jsonl`에 저장했지만 키워드 0건만으로 부재를 확정하지 않는다. 새 부재 라벨과 대조 문항은 현재 임계값 피팅에서 제외한다.

코퍼스 크기·FAQ 주제·대체 정답 수가 다르므로 **같은 데이터셋 안에서 엔진/검색 구조를 비교**한다. 통신사별 원시 Hit를 곧바로 우열로 해석하거나 네 데이터셋을 합쳐 큰 데이터셋 위주의 점수만 내지 않는다. 행 단위·목적별·분야별·연결 그룹별 지표와 분모를 병기하고, 대조쌍은 같은 그룹 단위로 비교한다. 같은 최종 Top-K 예산을 사용하며 A+B 후보 합집합의 recall은 최종 Top-K 점수와 구분한다.

## 출처와 검수

`faqs(1).jsonl`의 3,365행 중 3사 이외 724행을 제외하고, 같은 통신사의 동일 정규화 질문·답변 중복 106행을 묶어 신규 코퍼스 2,535개를 만들었다. 다른 질문이나 다른 언어 문서는 무조건 삭제하지 않고 별도 ID와 대체 정답 관계로 유지한다. 원본 행/ID/URL은 각 FAQ의 출처 필드에 보존한다. 같은 질문이지만 답변이 다른 7개 그룹은 원천 충돌 검수 대상으로 저장하고 질문 시드에서 보류했다.

원문에는 수집 시점의 상품·이벤트·날짜와 텍스트 추출 오류가 있다. 현재 통신사 정책의 사실성 평가가 아니라 **제공된 코퍼스에 대한 검색 실험**이다. 실제 사용자 실패 로그나 정책 버전 이력은 제공되지 않아 지어내지 않았다. DOCUMENT_ATTACK, 생성 답변 정확성, 도구를 통한 개인 계정 조회는 별도 실험이다. 긴 질문도 수백 자 규모로, 8K 토큰이나 다중 창 경계 검증을 대체하지 않는다.

`review/<dataset_id>.html`에서 질문, 사실, 전체 FAQ 답변, 원문 근거, 혼동 후보와 대체 정답 검수 후보를 확인할 수 있다. 같은 작성자의 확인을 독립 검수라고 기록하지 않는다. 모든 신규 라벨은 `eligible_for_final_benchmark: false`다. 정답을 추가/수정하면 사실 연결과 분할·입력 해시를 다시 고정해야 한다.

## 재현

이 폴더에서 Python 표준 라이브러리만 사용한다. Docker나 GPU 추론은 실행하지 않는다.

```powershell
python -X utf8 prepare_sources.py
python -X utf8 authoring/compile_alias_review.py
python -X utf8 build_dataset.py
python -X utf8 build_review.py
python -X utf8 test_dataset.py
python -X utf8 dataset.py --dataset kt --split development --allow-unreviewed
```

마지막 명령은 미검수 진단용 입력 확인이다. `--dataset`은 필수이며 `all`은 허용하지 않는다. `--allow-unreviewed`를 생략하면 독립 검수 전 질문의 로드를 차단한다. 기존 FAQ·v1/v2 질문 파일의 SHA-256 보존, 정답/모델 입력 분리, 다른 통신사 인덱스·캐시·검색 ID 차단, 알려진 그룹의 분할 누수, 대체 정답/복수 사실 채점을 포함한 **16개 검사**를 통과했다. 자동 검사는 의미적 정답의 완전성을 인증하지 않는다.
